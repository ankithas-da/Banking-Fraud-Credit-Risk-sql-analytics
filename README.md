# Card Fraud, Credit Risk & Portfolio Analytics

A synthetic but realistic retail card portfolio built for analytics practice and interview preparation.
It contains a generated dataset, a MySQL 8.0+ schema, **100 SQL questions across five business problems**, data-quality
checks, business solutions, and specifications for Power BI and Tableau dashboards.

> **All records in this repository are synthetic.** They are generated by `scripts/generate_dataset.py`.
> They are not Barclays data, not customer data, and do not reflect Barclays' internal methodology.

---

## Start here

You do not need to be an SQL expert. Each of the 100 questions is labelled **Medium** or **Advanced** and has a plain
business scenario. Work through one business problem at a time:

1. Load the data (section 4).
2. Run `sql/03_data_quality_checks.sql`. Every row should say `PASS`.
3. Open `sql/11_five_business_problems.sql`. Read the scenario, then the question, then the query.
4. Run one query, read the result, and write one sentence about what it means for the business.

## 1. The five business problems

The card business launched on 1 October 2021 and is analysed to 30 September 2026. Five teams need answers:

| # | Business problem | Who asks | Questions | Main file |
|---|---|---|---|---|
| 1 | **Card fraud losses**: where is fraud concentrated, and which controls would catch it without blocking genuine customers? | Fraud team | Q001–Q020 | `sql/04_fraud_analysis.sql` |
| 2 | **Credit risk exposure**: which accounts and customer groups carry the most risk before they fall into arrears? | Credit team | Q021–Q040 | `sql/05_credit_risk_analysis.sql` |
| 3 | **Collections and overdue payments**: how much is overdue, and which customers should be contacted first? | Collections team | Q041–Q060 | `sql/06_collections_analysis.sql` |
| 4 | **Transaction monitoring**: which transactions and accounts should analysts review first, with limited time? | Monitoring team | Q061–Q080 | `sql/07_transaction_monitoring.sql` |
| 5 | **Portfolio performance**: is the card book growing and healthy, and which segments need action? | Leadership | Q081–Q100 | `sql/08_portfolio_analysis.sql` |

**Where to read the questions:** `sql/11_five_business_problems.sql` contains all 100 questions, grouped by problem.
Each question is labelled **[Medium]** or **[Advanced]**:

- **Medium:** joins, grouping, `CASE` expressions, subqueries, CTEs and date functions.
- **Advanced:** window functions (`LAG`, `RANK`, `ROW_NUMBER`, `NTILE`, running totals), `ROLLUP` or `UNION ALL`.

Each question has a rationale, the tables and columns it uses, the expected output, the interpretation, and the
business decision it supports. The full list is in `docs/QUESTION_INDEX.md`. A browser-friendly version is in
`docs/QUESTIONS_AND_SOLUTIONS.html`. The five business solutions and the management conclusion are in
**`BUSINESS_SOLUTIONS.md`**.

## 2. Dataset

| Table | Rows | Grain |
|---|---|---|
| `customers` | 10,500 | one customer |
| `accounts` | 15,796 | one credit card account (14,971 open at 30 Sep 2026) |
| `merchants` | 33 | one merchant |
| `transactions` | 150,989 | one card transaction |
| `payments` | 327,682 | one monthly payment obligation |
| `date_dimension` | 1,826 | one calendar day in the window |

- **Reporting window:** 1 October 2021 to 30 September 2026 (60 complete months). Every month has transactions.
- **As-of date:** 30 September 2026. Days past due, account status and balances are measured at this date.
- **Currency:** GBP throughout.
- **Fraud labels:** 2,713 transactions (1.8%) are labelled. The label is synthetic ground truth for demonstration only.

Full column definitions, business rules, and limitations are in **`DATA_DICTIONARY.md`**.

## 3. Database schema

```
date_dimension                       customers ──< accounts ──< transactions >── merchants
(calendar_date)                      (customer_id)  (account_id)    (account_id, merchant_id)
                                                       │
                                                       └──< payments
                                                           (account_id, one row per statement cycle)
```

- Primary keys on every table; foreign keys from child to parent only; no circular relationships.
- `CHECK` constraints enforce the reporting window, non-negative amounts, valid status and payment values,
  and that `payments.due_date` falls after its statement date.
- Indexes support the expected analyses (account and time, merchant, channel and fraud, due date, DPD bucket).
- Financial amounts are `DECIMAL(12,2)`. Dates use `DATE` and `DATETIME`.
- `payments` has `UNIQUE (account_id, statement_date)`, so each account has at most one obligation per cycle.

## 4. Installation and import

**Requirements:** MySQL 8.0 or later. Python 3.10 or later with `pandas` and `numpy` is needed only if you want to
regenerate the data.

**Easiest route (no Python, no `local_infile`):** run the three files in `dump/` in order (see below), then run
`sql/11_five_business_problems.sql`.

**Plain SQL dump (no `local_infile` needed).** The full dataset is in three plain `.sql` files in `dump/`,
each under 30 MB. Run them in order:

```bash
mysql -u <user> -p < dump/01_schema_and_base_data.sql   # creates the database, all tables, base data
mysql -u <user> -p < dump/02_payments_part1.sql         # payments, first half
mysql -u <user> -p < dump/03_payments_part2.sql         # payments, second half
```

Or open each file in MySQL Workbench and run it. The files are generated from the CSVs by
`scripts/build_sql_dump.py`. Do not edit them by hand. Import takes several minutes.

**Status:** the dump was generated and its row counts were checked against the CSVs. It has **not** been imported into
a live MySQL server in this project's build environment, so run the import and then `sql/03_data_quality_checks.sql`
to confirm it.

**Alternative: load from CSV files (faster, needs `local_infile`).**

```bash
# 1. Create schema (drops and recreates barclays_card_risk)
mysql -u <user> -p < sql/01_create_schema.sql

# 2. Load the CSVs (run from the repository root; needs local_infile)
mysql --local-infile=1 -u <user> -p barclays_card_risk < sql/02_load_or_import_data.sql
```

If `local_infile` is off, run `SET GLOBAL local_infile = 1;` as an administrator, or load each CSV with
MySQL Workbench's Table Data Import Wizard in the order listed in `02_load_or_import_data.sql`.

## 7. KPI definitions (summary)

| KPI | Definition | Source |
|---|---|---|
| Fraud rate % | fraud-labelled transactions ÷ all transactions | transactions |
| Fraud value share % | fraud-labelled amount ÷ total amount | transactions |
| Risk tier | Tier 1 High if DPD ≥ 30 or utilisation > 100%; Tier 2 if utilisation ≥ 60% or score < 580; Tier 3 if utilisation ≥ 30% or score < 670; else Tier 4 | accounts, customers |
| 30+ DPD rate % | obligations with DPD ≥ 30 at 30 Sep 2026 ÷ all obligations | payments |
| Overdue amount | outstanding balance where DPD > 0 at 30 Sep 2026 | payments |
| Collection rate % | amount paid ÷ amount due | payments |
| Utilisation | current balance ÷ credit limit (open accounts) | accounts |
| Precision | fraud flagged ÷ all flagged (rule) | transactions |
| Recall | fraud flagged ÷ all fraud | transactions |

Full definitions are in `DATA_DICTIONARY.md`.

## 8. Key limitations

- **Due dates after the period end (known issue).** 9,770 payment obligations have a `due_date` between 1 and
  19 October 2026, which is after the reporting period. Of these, 1,104 were paid early in September (allowed
  under the early-payment rule), and 8,666 are unpaid obligations that are current (not yet due) at the
  as-of date. These come from statements dated in the last 21 days of the period. The brief asks that due dates
  stay within the period, so this must be fixed by generating statements only where the due date falls inside
  the period. Fixing it changes the record counts and the computed results. Until then, treat these
  obligations as open, not-yet-due items.
- **Synthetic data.** Patterns were designed into the generator. Strong results (for example the card-testing burst rule) reflect the design, not real-world behaviour.
- **No revenue, interchange, interest, recovery or loss data.** Q088 says so. Profitability is not analysed.
- **No month-end snapshots.** Account status, balance and utilisation are current-state values at 30 Sep 2026. The project does not claim trends from them.
- **No true roll rates.** Delinquency trends use due-date cohorts. Transitions use consecutive statement cycles (Q057). A DPD roll rate would need monthly snapshots.
- **No charge-off.** Unpaid obligations stay open to the as-of date, so some are almost five years old.
- **Early months are thin.** The book launches on 1 October 2021 with no pre-existing customers, so the first months have few transactions (7 in October 2021). Compare rates only from mid-2022 onward.
- **Partial years.** 2021 and 2026 are partial. Compare per-month values.
- **Rule-based tiers are not a credit-scoring model.** They are transparent business rules. They have not been calibrated to losses or tested for fairness beyond the descriptive view.
- **Fraud labels are not confirmed outcomes.** The monitoring analysis separates observable rules from the label, which is used only to measure rules.

## 9. Reproducibility

The dataset is fully determined by the code and a fixed seed (`20261001`). To regenerate and re-check everything:

```bash
bash scripts/run_pipeline.sh
```

This runs `generate_dataset.py`, `validate_dataset.py`, `compute_findings.py` and `check_questions.py`.
It does not run the SQL. Run the SQL files as described in section 5.

The scripts:

| Script | Purpose |
|---|---|
| `scripts/generate_dataset.py` | Generates the CSVs in `data/` (fixed seed, enforced date window) |
| `scripts/validate_dataset.py` | 41 integrity checks, writes `reports/validation_report.md` |
| `scripts/compute_findings.py` | Computes the findings in `reports/findings.md` using the same definitions as the SQL |
| `scripts/check_questions.py` | Checks the 100 questions for numbering, headers and placeholders; writes `docs/QUESTION_INDEX.md` |
| `scripts/build_sql_dump.py` | Rebuilds the three files in `dump/` from `data/` |
| `scripts/build_questions_html.py` | Rebuilds `docs/QUESTIONS_AND_SOLUTIONS.html` from the SQL files |
| `scripts/run_pipeline.sh` | Runs the first four scripts above in order |

## 11. Using this project in a portfolio

- **Lead with the verification table** above. It shows that you separate what you executed from what you did not, which is the habit a banking analytics team looks for.
- **Walk through one business problem end to end**, for example fraud: the question, the SQL, the result in `findings.md`, the decision, and the limitation (the card-testing result is circular by construction).
- **Explain the design choices**: why DPD is measured on the outstanding amount at the as-of date, why fraud value and frequency are separate, why rules use observable features and the label only for measurement, and why there is no fact-to-fact join in the dashboards.
- **Be ready for the hard questions**: what the data cannot tell you (revenue, true roll rates, real fraud outcomes), and what additional data you would need.
- **Be precise about status.** Say "the Python validation is executed and passes; the SQL is written and parsed; I ran it on MySQL on [date]" only after you have actually done so.
